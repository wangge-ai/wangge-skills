# 状态、重试与幂等

用状态机定义 RPA 的正确性。不要用“流程走完了”或“目录里有文件”代替状态闭环。

## 1. 先定义任务身份

区分以下标识：

- `run_id`：本次启动实例，用于串联日志；每次启动都不同。
- `task_key`：一次业务任务的稳定身份，用于幂等和断点续跑。
- `item_key`：任务内业务项的安全标识，如脱敏账号 ID、店铺序号或文件 ID。
- `attempt`：同一 `task_key + item_key` 的尝试次数。

按业务需要从以下维度构造 `task_key`：

```text
workflow + tenant + data_type + business_start + business_end
+ query_end + purpose + rerun_batch + schema_version
```

遵守这些规则：

1. 规范化日期、空值、大小写和字段顺序后再序列化或散列。
2. 不把账号、密码、Token 等秘密写入键、路径或日志。
3. 分开保存业务闭区间结束日和网页查询右开区间结束日。例如业务截止 7 月 31 日，网页可能输入 8 月 1 日。
4. 仅当业务确实要求同一日期范围生成两份不同用途的产物时，把 `purpose` 纳入键；否则合并重复任务。
5. 用新的 `rerun_batch` 表示强制重跑，不通过删除旧状态或旧产物制造重跑。

## 2. 使用显式状态机

建议的最小状态集：

| 状态 | 默认终态 | 默认可重试 | 说明 |
|---|---:|---:|---|
| `pending` | 否 | 是 | 尚未开始 |
| `running` | 否 | 是 | 已进入有副作用的处理 |
| `success` | 是 | 否 | 产物已校验并归档 |
| `no_data` | 是 | 否 | 查询完成且页面明确返回无数据 |
| `captcha_failed` | 否 | 是 | 合法验证方式未成功 |
| `login_failed` | 否 | 是 | 普通登录或风控异常 |
| `credential_failed` | 由项目决定 | 默认否 | 密码错误、账号停用等；改变策略前确认 |
| `failed` | 由错误码决定 | 由错误码决定 | 其他稳定分类的失败 |

至少保存：

```text
task_key, item_key, status, stage, error_code, attempt,
updated_at, run_id, artifact_path, message_safe
```

只允许明确迁移：

```text
pending -> running
running -> success | no_data
running -> captcha_failed | login_failed | credential_failed | failed
非终态 -> running（仍有预算时重试）
```

不要把 `running`、未知状态、空状态或命令异常当成已完成。

## 3. 强制关闭 `running`

在即将执行登录、查询、下载等有副作用动作前写入 `running`。在所有正常、异常和提前退出分支中执行以下闭环：

1. 写入终态或明确的非终态状态。
2. 写入稳定 `stage` 和 `error_code`。
3. 关闭当前业务项拥有的页面、弹窗或会话。
4. 返回父级业务项循环，或在致命配置错误时终止整批。

为进程崩溃保留陈旧 `running` 检测。启动时按租约或更新时间识别陈旧记录，将其转成 `failed/interrupted` 或直接纳入可重试队列；不要跳过陈旧 `running`。

把状态写入设计为原子更新：写临时文件、刷新并替换目标文件，或使用具备事务语义的存储。不要留下半截 JSON。

## 4. 统一 `should_run`

按以下顺序判断：

1. 用完整 `task_key + item_key` 查状态。
2. 相同任务键已是允许跳过的终态：返回 `SKIP`。
3. 状态为非终态且仍有重试预算：返回 `RUN`。
4. 状态为近期活跃 `running`：按并发租约策略返回 `BUSY`，不要并发重复处理。
5. 状态为陈旧 `running`：先恢复为可重试失败，再返回 `RUN`。
6. 没有状态：返回 `RUN`。

不要仅因文件存在就跳过；也不要仅因状态写了 `success` 就相信产物。验收时同时核对状态、产物路径、文件有效性和任务键。

## 5. 分开三层有限重试

### 节点级重试

仅用于短暂 UI、网络或文件锁异常。限制为少量次数和短间隔。不要对密码错误、账号停用、持续验证码或业务规则错误反复点击。

### 业务项级重试

重新打开干净页面或会话后重试同一业务项。每次都增加 `attempt`，重新检查状态并执行资源清理。

### 批次级有限补跑

完成一轮全部业务项后，再运行固定次数的补跑轮次。第二轮及以后仍调用 `should_run`：

- 终态业务项立即 `SKIP`。
- 非终态业务项才等待冷却并重试。
- 把冷却等待放在 `should_run` 之后，避免所有终态项逐一等待。

控制总预算：

```text
总尝试上限 <= 节点重试上限 × 业务项尝试上限 × 批次轮数
```

避免三层同时处理同一种错误。为每个错误码指定唯一主重试层。

## 6. 建立重试策略表

为每个稳定错误码明确：

| error_code | stage | status | 主重试层 | 最大次数 | 冷却 | 清理动作 |
|---|---|---|---|---:|---:|---|
| `element_timeout` | 任意 | `failed` | 节点/业务项 | 项目配置 | 短 | 视页面状态 |
| `login_timeout` | login | `login_failed` | 批次 | 项目配置 | 中 | 关闭登录页 |
| `login_slider_failed` | login | `captcha_failed` | 批次 | 少量 | 中 | 关闭当前页 |
| `business_slider_failed` | business | `captcha_failed` | 批次 | 少量 | 中 | 关闭当前页 |
| `credential_error` | login | `credential_failed` | 默认不自动重试 | 0 | 无 | 关闭当前页 |
| `download_timeout` | download | `failed` | 业务项/批次 | 项目配置 | 中 | 隔离残留文件 |
| `archive_failed` | archive | `failed` | 业务项 | 项目配置 | 短 | 保留源文件 |

使用稳定、机器可读的错误码；把动态页面文本放入脱敏消息，不要把整段页面文本当错误码。

## 7. 正确嵌套日期任务

先生成日期任务清单，再执行补跑和业务项循环：

```text
日期任务清单循环
  ├─ 解析本任务的业务日期与网页查询日期
  ├─ 构造独立 task_key / 状态文件 / 输出命名
  └─ 有限补跑循环
       └─ 业务项循环
            ├─ should_run
            ├─ SKIP 或 RUN
            └─ 状态闭环与资源清理
```

不要把日期任务循环放进业务项循环，否则会重复登录、污染状态键并难以续跑。不要让多个日期任务共用不含日期和用途的状态文件。

在执行前处理重复任务：

- 日期范围和用途都相同：合并。
- 日期范围相同但业务要求两份不同用途产物：保留两项，并把 `purpose` 纳入任务键和文件名。
- 空日期范围：显式记录 `EMPTY_TASK` 或跳过原因，不进入网页流程。

## 8. 验收不变量

逐项验证：

- 每个 `RUN` 最终都有终态或明确非终态。
- 不存在永久残留 `running`。
- 相同任务键重跑时，终态跳过、非终态重试。
- 强制重跑使用新批次键且不覆盖旧产物。
- 归档成功前不写 `success`。
- `no_data` 来自明确查询结果，而不是下载缺失。
- 第二轮补跑只等待和处理非终态业务项。
- 每个日期任务拥有独立状态、日志上下文和产物命名。
- 日志可用 `run_id + task_key + item_key + attempt` 重建完整时间线。
