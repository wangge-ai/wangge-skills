# DESIGN.md

本文件用于提高 Codex 在前端、网页、工作台、可视化页面和 HTML 交付中的审美稳定性。核心原则不是“做得好看点”，而是让 Codex 在写代码前先完成主题提取、视觉方向探索、设计系统定义和反 AI 味自检。

它更像一份全局审美规则：负责约束设计流程、反模式和质量门槛。它不提供一个可复制到所有项目的固定风格。具体项目还应补充自己的品牌、颜色、字体、组件和页面密度规则。

## 0. 使用规则

凡是涉及 UI、网页、HTML、React/Vue 组件、仪表盘、长图、可视化报告或交互工具，Codex 必须先阅读本文件，再开始设计和实现。

不得直接进入代码。必须在内部按下面顺序工作：

1. 产品理解
2. 主题提取
3. 视觉方向探索与选择
4. 设计系统
5. 实现
6. 视觉批评与 QA
7. 反 AI 味自检

具体执行深度按“任务尺度控制”调整；小改动可在内部快速完成判断，不必重新建立完整设计系统。新页面和 redesign 必须先完成主题提取与方向选择，再进入 token 和实现。

如果某一项没有完成，不要交付。用户要求简洁输出时，可以只展示关键设计决策、实现结果和自检结论，不要为了展示流程而输出冗长分析。

## 1. 产品理解

设计前先判断这个页面真实服务的对象和任务。

必须回答：

- 这个页面、应用或组件服务谁？
- 用户来这里完成什么任务？
- 页面应该给人的感觉是什么？
- 它是营销页、工作台、数据后台、内容产品、工具产品、游戏、品牌官网，还是内部系统？
- 信息密度应该高还是低？
- 用户更需要效率、信任、探索、沉浸、秩序、趣味，还是情绪感染？

不同类型的产品应有不同审美。不要把所有页面都做成 SaaS 落地页。

## 2. 主题提取与视觉方向探索

先从主题本身找视觉线索，不要从“好看的 UI 风格”开始。设计必须回答：这个产品如果被换成另一个行业，页面还会不会几乎一样？如果会，说明还没有提取到主题。

### 主题提取

在选择颜色、字体或组件前，先在内部写一张主题卡：

- 具体对象：不是“一个平台”，而是一个可被看见、触摸或描述的对象、行业或工作场景。
- 具体受众：谁使用，它对什么细节敏感，什么会让它不信任。
- 单一任务：这张页面最重要的一个动作或判断是什么。
- 主题世界：它的材料、工具、场所、文档、仪器、工艺、时间感、语言习惯和真实约束是什么。
- 现有证据：项目已有界面、品牌规范、截图、图片、产品实物或用户提供的参考里，哪些元素值得延续。

主题世界是视觉选择的来源。研究资料库可以来自档案盒、标签、批注和采访现场；电商出图工具可以来自样品、打样单、色卡和拍摄台；开发者工具可以来自日志、队列、图谱和时间序列。不要把它们都翻译成同一套深色面板或暖白色编辑页。

### 方向探索

新页面或 redesign 至少在内部形成 2–3 个方向草案。每个草案只需写清：视觉命题、主题依据、排除的套路、首屏锚点和一个有理由的审美风险。

选择最终方向时，必须能说明为什么它比另两个方向更适合任务。不要把探索过程完整倾倒给用户；默认只展示最终选择和关键理由。

审美风险不是无端复杂。它可以是非对称构图、一种不常用但可读的字体关系、一个来自真实工作材料的视觉锚点，或一种克制但非常规的信息结构。风险必须改善识别度或任务理解。

### 选择视觉方向

不要使用“现代、简洁、高级、科技感”这种空泛词。每次 UI 工作必须先选择一个明确的风格锚点，并说明为什么适合当前产品。

以下是可用于组合和推演的词汇，不是模板库。它们必须由主题证据选择，而不是因为上一页用得好看：

- Swiss editorial：瑞士平面、强网格、克制颜色、清晰排版，适合内容、研究、品牌说明和专业叙事。
- Dense data workspace：高信息密度、表格、分栏、工具栏、清晰状态，适合后台、运营台、数据分析和内部系统。
- Industrial terminal：深色底、单色信号色、等宽数字、硬朗边界，适合开发者工具、监控、自动化、机器感产品。
- Luxury editorial：大字号、留白、细线、克制动效，适合高端品牌、作品集、精品内容。
- Brutalist utility：粗边框、硬阴影、强对比、原始网页感，适合实验性工具、创意产品和有态度的活动页。
- Organic warm：自然色、柔和层次、纸感或材质感，适合教育、生活方式、人文内容和陪伴型产品。
- Retro-futuristic：霓虹、CRT、扫描线、复古未来感，适合游戏、音乐、活动、概念页。
- Lo-fi risograph：纸张颗粒、错印、手作感，适合独立出版、创意社区、艺术项目。
- Playful product：鲜明色块、轻微夸张、友好图形，适合轻工具、儿童/教育、消费产品。

选择后必须说明：

- 为什么这个风格服务当前产品，而不是为了炫技。
- 哪些主题证据支撑这个选择。
- 页面最有记忆点的视觉动作是什么。
- 哪些地方必须克制，避免过度设计。
- 哪个看似安全的默认方案被主动排除了，为什么。

## 3. 先定义设计系统

写代码前先定义设计系统。设计系统要能落到 CSS token、组件状态和响应式规则上。

token 是视觉方向的翻译，不是视觉方向本身。没有完成主题提取和方向选择时，不得先用一套熟悉的 token 把页面做出来再补理由。

本文件提供方法，不提供具体项目的最终 token。每个项目应把空 token 补成真实值。

禁止把空 token 原样写入最终代码。所有出现在代码中的 token 必须有真实值、fallback，或继承自现有项目变量。

基础 token 模板：

```css
:root {
  --bg: ;
  --surface: ;
  --surface-2: ;
  --text: ;
  --muted: ;
  --border: ;
  --accent: ;
  --accent-2: ;
  --danger: ;
  --success: ;

  --font-display: ;
  --font-body: ;
  --font-mono: ;

  --space-1: ;
  --space-2: ;
  --space-3: ;
  --space-4: ;
  --space-5: ;

  --radius-sm: ;
  --radius-md: ;
  --radius-lg: ;

  --shadow-sm: ;
  --shadow-md: ;
  --shadow-lg: ;

  --duration-fast: 150ms;
  --duration-base: 220ms;
  --ease-standard: cubic-bezier(.2, .8, .2, 1);
}
```

### 色彩

必须定义语义化颜色，而不是随手挑色。

颜色 token 至少包括 `--bg`、`--surface`、`--surface-2`、`--text`、`--muted`、`--border`、`--accent`、`--accent-2`、`--danger`、`--success`。

要求：

- 只有一个主强调色，必要时再加一个辅助强调色。
- 背景、容器、边框、正文、弱文本、状态色要有明确角色。
- 不要默认使用紫色/蓝色渐变白底。
- 不要默认灰底白卡片。
- 不要让界面读起来像同一色系的堆叠，必须有主次、冷暖或明暗对比。
- 不要把上一项目的调色板迁移成默认答案。莫兰迪暖色、深色工业感、报纸色调等都只能在主题和项目规范支持时使用。

### 字体

必须定义：

- 标题字体
- 正文字体
- 数字/代码字体，如果产品需要

要求：

- 不要把 Inter、Roboto、Arial、system-ui 当成默认主视觉答案。
- 如果无法加载外部字体，必须通过字号、字重、字距、行高、排版比例和字体栈组合制造明确风格。
- 标题和正文要有性格差异。
- 字号、行高、字重、字距要形成层级。
- 避免所有文字都是 16px、400 weight。
- 工具型界面可以更紧凑；品牌页、作品集和内容页可以更有编辑感。

### 布局

必须定义：

- 页面最大宽度
- 栅格或分栏方式
- section 间距
- 卡片/面板间距
- 移动端断点
- 信息密度

要求：

- 不要默认三列 feature grid。
- 不要所有卡片同尺寸、同圆角、同阴影。
- 可以使用非对称、错位、重叠、强留白或密集工具布局，但必须服务内容。
- 页面首屏要让用户立即理解产品、对象或任务。
- 移动端不能横向滚动，关键操作不能被挤压到不可用。

### 组件

至少考虑这些组件的视觉和状态：

- Button
- Card / Panel
- Input / Select / Textarea
- Table / List
- Navigation
- Modal / Drawer，如果需要
- Empty state
- Loading state
- Error state

要求：

- 所有交互元素必须有 hover、focus、active、disabled 状态。
- focus 状态必须清晰，支持键盘导航。
- 图标必须来自同一风格；不要混用多个 icon family。
- 不要用 emoji 当正式图标，除非产品风格明确需要。
- 卡片只能用于真正需要被框住的对象，不要把页面 section 都做成浮动卡片。
- 不要卡片套卡片、pill 套 pill、容器无限嵌套。

### 动效

动效必须表达层级、状态或空间关系。

要求：

- 常规交互动效控制在 150-300ms。
- 支持 `prefers-reduced-motion`。
- 一个高质量入场动效胜过一堆零散小动画。
- 不要装饰性浮动粒子、脉冲圆点、无意义 parallax。
- 不要为了“高级感”滥用 blur、glass、shadow。

## 4. 反 AI 味黑名单

以下内容是高概率收敛模板，默认禁止。它们在特定 brief 中可以成立，但必须能解释为什么主题、任务或现有品牌让它必要：

- 紫色/蓝色渐变白底。
- 玻璃拟态卡片堆叠。
- 三列 feature grid。
- “Get Started / Learn More” 默认 CTA。
- 大量圆角白卡片加灰色背景。
- card 套 card 套 pill。
- floating orb、blinking dot、live badge。
- 无意义的 mock dashboard 截图。
- “Built for teams”“All-in-one platform” 这类空泛文案。
- 所有页面都像 SaaS landing page。
- Lucide 图标滥用。
- 渐变文字滥用。
- 阴影、模糊、玻璃效果滥用。
- 只有装饰没有信息结构的背景。
- 暖米白底、高对比衬线和陶土强调色被不加判断地组合成“高级感”。
- 近黑背景加酸性绿、朱红或霓虹信号色被不加判断地组合成“专业工具感”。
- 细线、零圆角和报纸式密栏被不加判断地组合成“编辑感”。
- `01 / 02 / 03`、眉标、分隔线和标签只起装饰作用；编号只有在真实顺序、流程或类型编号存在时才可使用。

## 5. 按产品类型调整审美

### 工作台 / 后台 / 数据产品

优先级是效率、扫描、比较、重复操作。

- 信息密度可以高，但必须分组清晰。
- 使用紧凑工具栏、表格、筛选、状态标签、明确分栏。
- 视觉要安静、克制、专业。
- 不要做营销页式大 hero、装饰插画和过度卡片化。

### 营销页 / 品牌页

优先级是记忆点、信任和叙事节奏。

- 首屏必须明确品牌、产品或对象。
- H1 要直接表达品牌/产品/类别，不要只写抽象口号。
- 必须有真实视觉资产或强视觉场景。
- 支持文案节奏，而不是靠堆卡片填页面。

### 工具 / 交互应用

优先级是直接可用。

- 第一屏就是可操作界面，不要先做介绍页。
- 控件要完整：模式、参数、状态、结果、错误反馈。
- 固定格式元素要有稳定尺寸，避免 hover 或内容变化导致布局跳动。
- 复杂工具要优先让主任务路径顺畅。

### 数据可视化 / 报告

优先级是可信、可读、可比较。

- 图表标题必须描述正在展示的指标和范围。
- 不要用炫酷样式压过数据。
- 颜色必须有分类或状态意义。
- 图例、轴、单位、时间范围要清楚。
- 结论和图表必须互相支持。

## 6. 参考视觉规则

如果用户提供截图、参考网站、品牌风格、竞品页面或视觉资产，先提取视觉语言，再重新组合成适合当前产品的设计系统。

必须提取：

- 色彩结构：背景、强调色、状态色、明暗关系。
- 字体气质：标题、正文、数字、字号层级。
- 间距和密度：留白、栅格、分栏、内容密度。
- 组件语言：圆角、边框、阴影、图标、按钮、输入框。
- 动效语言：节奏、方向、层级和状态反馈。
- 内容结构：首屏重点、导航方式、主任务路径。
- 主题证据：参考中哪些材料、场景、物件、行为或行业语言值得转换成当前页面的视觉线索。

限制：

- 不要 1:1 抄袭品牌资产、logo、插画或专有布局。
- 可以借鉴设计原则，但必须改写成当前项目自己的 token、组件和页面结构。
- 如果参考风格与当前产品任务冲突，以当前产品任务为准。

## 7. 实现要求

代码必须：

- 可运行。
- 结构清晰。
- CSS token 化。
- 响应式。
- 可访问。
- 有真实内容层级。
- 有状态反馈。
- 视觉风格统一。

如果是 HTML/CSS/JS：

- 优先使用原生 CSS。
- 不要依赖过多外部库。
- CSS 中写清楚设计 token。
- 保持文件结构可维护。

如果是 React / Vue：

- 组件拆分要服务理解和复用。
- 样式系统保持一致。
- 不要为了炫技引入不必要复杂度。

## 8. 质量门槛

交付前至少满足：

- 正文对比度不低于 4.5:1。
- 常规正文不低于 14px，优先 16px。
- 可点击区域不小于 44px。
- focus 状态必须肉眼可见。
- 移动端 360px 宽度不能横向滚动。
- 常规动效控制在 150-300ms。
- 同一页面最多一个主强调色，一个辅助强调色。
- 视觉容器嵌套尽量不超过两层；复杂业务结构可以有更深 DOM，但不能表现为 card 套 card 套 pill 的视觉噪音。
- 交互元素必须有 hover、focus、active、disabled 状态。
- 关键界面必须考虑 loading、empty、error 状态。
- 固定格式控件、面板、棋盘、画布、表格和工具栏必须有稳定尺寸，不能因状态变化跳动。

如果技术环境无法完全验证某项门槛，必须说明未验证项，并尽量用代码约束降低风险。

## 9. 视觉 QA

交付前必须自检：

- 是否能说出页面的具体对象、受众和单一任务？
- 页面是否从主题世界获得了至少一个可识别的视觉线索，而不是从通用风格清单里取材？
- 如果把行业名称替换掉，这套设计是否仍然几乎不变？如果会，先回到主题提取。
- 编号、眉标、边线、标签和动效是否都在表达真实信息，而不是装饰？
- 页面是否有明确品牌气质？
- 是否像真实产品，而不是 AI demo？
- 是否避开了默认渐变、玻璃卡片、三列卡片等套路？
- 字体是否有性格和层级？
- 色彩是否有语义和主次？
- 布局是否有节奏？
- 组件状态是否完整？
- 移动端是否可用？
- 是否有 hover / focus / active / disabled？
- 是否有 loading / empty / error 状态？
- 是否支持键盘导航？
- 色彩对比是否基本合格？
- 动效是否有目的？
- 容器嵌套是否过深？
- 文案是否具体，而不是模板话术？

任一项失败时，先修复失败区域，再交付。

## 10. 项目级覆盖规则

本文件是全局审美规则，不等于具体项目的完整设计系统。

如果项目已有更具体的 `DESIGN.md`、品牌规范、截图、参考网站、Figma 或现有产品界面，以项目级规则为准。本文件用于约束 Codex 的审美流程、反 AI 味黑名单和视觉 QA。

每个具体项目应尽量补充：

- 品牌关键词
- 目标用户
- 具体颜色 token
- 具体字体或字体风格
- 组件圆角、边框、阴影规则
- 页面信息密度
- 允许的视觉风格
- 禁止的视觉风格
- 典型页面布局
- 关键组件状态
- 可接受的参考风格
- 主题世界与可用视觉材料，例如产品、环境、工具、文档、纹理、摄影、数据或行业语言。
- 已选方向和主动排除的方向。
- 项目级 token。具体调色板只能在这里定义；例如“米白纸上的工作手册”可采用 Organic warm + Swiss editorial 和莫兰迪暖色 token，但不能回写成全局默认。

当全局规则与项目级规则冲突时：

- 品牌、颜色、字体、组件规范以项目级规则为准。
- 可访问性、状态完整性、移动端可用性和反 AI 味约束仍必须满足。
- 如果项目级规则本身造成可用性或可访问性问题，先指出风险，再给出替代方案。

## 11. 输出克制

Codex 必须完成产品理解、审美方向、设计系统和视觉 QA，但不一定全部展示给用户。

如果用户要求直接交付代码或文件，可以只输出：

- 简短设计决策
- 实现结果
- 关键自检结论

不要为了展示流程而输出冗长分析。内部做足，外部克制。

## 12. Codex 输出格式

涉及 UI 的任务，Codex 应在工作中完成下面步骤：

1. 产品理解
2. 主题提取
3. 视觉方向探索与最终选择
4. 设计系统
5. 实现结果
6. 视觉 QA
7. 已修复的问题或仍存在的限制

如果用户没有要求展示完整过程，最终回复应短，只说明做了什么、验证了什么、还有什么限制。

## 13. 任务尺度控制

Codex 应根据任务大小决定设计介入程度，避免小需求被过度设计。

- 小改动：只保持现有设计系统一致，不重新定义整体风格。
- 局部组件：补齐该组件状态、间距、可访问性，不重做整页。
- 新页面：必须完成审美方向和设计系统。
- 新产品/网站：必须建立完整项目级 `DESIGN.md`。
- 已有项目：优先延续现有视觉语言，不要因为本文件而强行换风格。

如果用户明确要求 redesign、重做视觉、换风格或提升审美，可以扩大设计介入范围。否则默认做最小必要改动。

## 14. 现有项目优先规则

在已有项目中修改 UI 前，必须先读取现有页面、组件、样式文件和设计 token。

优先复用：

- 已有颜色变量
- 已有字体规则
- 已有间距尺度
- 已有圆角、边框和阴影规则
- 已有组件状态
- 已有布局模式

除非用户明确要求 redesign，否则不要引入一套全新的视觉语言。

如果现有项目没有清晰 token，应从现有界面中归纳隐含规则，再以最小变更补齐当前任务需要的样式。

## 15. 渲染检查

如果技术环境允许，交付 UI 前必须运行或预览页面，检查实际渲染效果，而不是只看代码。

重点检查：

- 首屏是否成立。
- 移动端是否破版。
- 字体是否加载失败。
- hover / focus / active 是否可见。
- 是否出现横向滚动。
- 动效是否过度。
- 真实内容是否溢出。
- 状态变化是否导致布局跳动。
- 截图、图片、图标、图表和 canvas 是否真实渲染。

如果无法运行或预览，必须在最终回复中说明未做渲染检查，并指出已用哪些代码约束降低风险。

## 16. 外部资源与可访问性补充

使用字体、图片、图标、图表库或 CDN 前，必须确认项目允许外部资源。

外部资源要求：

- 优先复用项目已有依赖和资产。
- 外部字体必须提供 fallback。
- 不要热链接不确定授权的图片。
- 如果网络不可用，界面仍应保持可读和可用。
- 图标库只能使用一种风格体系。

可访问性最低要求：

- 表单控件必须有可见 label 或明确 `aria-label`。
- 页面必须有合理 heading 层级。
- 不能只依靠颜色传达状态。
- icon-only button 必须有 `aria-label`。
- focus 顺序应符合视觉阅读顺序。

## 17. 系统级实现协议

当任务是新产品、整页 redesign、多个页面统一，或用户明确要求系统级改造时，必须把设计从页面级样式提升为四层系统。这个协议约束实现方式，但不替代前面的主题提取和视觉方向探索。

### Layer 0：Tokens

- 所有页面共享一个 token 文件，作为颜色、字号、字重、行高、间距、圆角、边框、断点和动效的单一事实来源。
- 业务 CSS 不得直接写颜色、字号、间距或阴影值；先在 token 层定义语义，再由组件引用。
- 只有一个主强调色。分类色只表达内容类别，状态色只表达状态，不能为了装饰或平衡版面随意换色。
- 系统如果采用无阴影方向，必须全局保持无阴影；层次用背景层级、边框和留白表达。
- 空 token 不得进入最终代码。检查脚本扫描业务 CSS 时应排除 token 定义文件，但业务文件中出现硬编码颜色或尺寸应失败。

### Layer 1：Layout Primitives

页面只通过 `AppShell`、`Stack`、`Row`、`Grid` 组合布局。侧栏宽度、主区 gutter、页面上下内边距、栅格列数和 section 间距必须由 token 锁定。

- `AppShell` 每页只能有一个。
- 页面不能为自己重新发明侧栏、header、指标条或栅格。
- DOM 可以因业务复杂而更深，但视觉容器不能形成 card 套 card 套 pill 的噪音。

### Layer 2：Components

先建立封闭的组件集合，再进入业务页面。至少包括 `PageHeader`、`MetricRow`、`SidebarNav`、`Button`、`Chip`、`Card`、`TableRow`、`Input` / `Select`、`EmptyState`、`Callout`。

- 每个组件放在独立文件中，由一个组件入口统一导入。
- 每个交互组件必须实现 rest、hover、active、focus-visible、disabled；需要异步时补 loading，需要数据边界时补 empty、error、selected。
- `Chip` 颜色由内容分类决定，不由页面位置或审美点缀决定。状态 chip 默认使用中性语义。
- `EmptyState` 必须是受约束的组件，不能用一个巨型面板占满首屏。
- 组件状态必须在 `states.html` 中集中展示，作为渲染后的视觉 QA 对照物。

### Layer 3：Templates

页面必须声明并归属于有限模板集合。默认使用：

- `T1 Workspace`：工作台、列表、表格、任务队列。
- `T2 Editor`：主编辑区加参考或预览区。
- `T3 Detail`：单条记录、证据或长内容详情。

模板负责页面骨架，业务页面只填充真实内容。新增页面结构无法归入模板时，先扩展模板和组件系统，再写页面样式。

### 系统级迁移顺序

1. 从现有页面、截图和业务对象提取主题，探索至少两个视觉方向并选定一个。
2. 冻结项目 token 文件，删除旧页面中的独立颜色、字号、间距和阴影规则。
3. 建立 Layer 2 组件文件与 `states.html`。
4. 建立 T1 / T2 / T3 空壳模板。
5. 用模板重铸现有页面，不在旧样式表上继续叠补丁。
6. 用桌面和移动端截图并排审查；问题回到 Layer 0、1、2 修复，不在页面层继续造例外。

### 系统级验收

多个页面并排查看时，允许内容不同，不允许视觉规则漂移。至少检查：侧栏、PageHeader、指标条、卡片、Chip、空状态、边框、间距、按钮状态和移动端断点是否一致；同时确认没有深色 hero 与浅色主区混用、装饰性渐变、玻璃效果、非产品浮层或输入法等外部元素。

最终目标：让每次 UI 输出都像真实产品，有明确风格、清晰系统、完整状态和可验证的视觉质量，而不是默认 AI demo。

## 18. 跨页面一致性闸门

当同一产品存在两个及以上相关页面时，先把它们视为同一个渲染系统，再修改其中任意一页。页面层不能重新发明系统层。

交付前必须检查：

- AppShell、导航形态、侧栏宽度和主区留白是否共享同一实现；同一产品不允许一页是顶部深色导航，另一页是浅色侧栏，除非项目模板明确声明不同壳层。
- 所有相关页面的 H1 是否引用同一个 `--fs-h1`、`--lh-h1` 和字距 token；禁止页面 CSS 覆盖 H1 尺寸。扫描业务 CSS 时，`font-size: <number>px` 应为 0，token 定义和第三方文件除外。
- PageHeader 是否按同一个槽位顺序组合：eyebrow、H1、lead、actions。指标、筛选提示和页面私有导航不得塞入 header，除非共享组件已有明确变体。
- 主按钮是否引用同一个 primary 组件和主强调色；ghost 或 secondary 只可用于次要动作。
- 每个内容区是否明确选择 Card 或 List 之一：卡片使用统一 padding 与 gap，列表使用统一 row height；禁止分隔线列表和卡片外框混搭。
- 色相、状态色和 chip 语义是否来自同一 token 文件；不得出现页面私有蓝橙、正绿或临时高饱和强调色。

如果任一页面的导航、类型、标题、header 或主按钮不来自共享 Layer 0/1/2，就不要继续为它写局部覆盖。先将页面迁回已有 T1/T2/T3 模板，或先扩展共享模板，再填业务内容。

验收时把相关页面放在同一 viewport 并排渲染，比较 AppShell 几何、H1 计算字号、PageHeader 顺序、主按钮颜色和 `--accent`。非内容导致的差异一律视为系统层缺陷，回到 token、primitive、component 或 template 修复。
