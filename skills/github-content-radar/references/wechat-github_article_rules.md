# GitHub 公众号选题规则

## 1. 选题判断

一个 GitHub 仓库值得写，不是因为 Star 高，而是它能被翻译成读者能用的动作。

优先写：

- AI Agent
- Claude Code / Codex / Cursor / Gemini CLI / GLM 相关工具
- Skill / MCP / 插件
- 内容生产工具
- HTML / PPT / 图文 / 视频生成工具
- 知识库 / 记忆 / RAG / 代码图谱
- 浏览器自动化
- 飞书 / Obsidian / GitHub 工作流
- 免费替代付费工具

少写：

- 纯算法论文复现
- 纯开发框架更新
- 无应用场景的底层库
- 无截图无 Demo 的项目

## 2. 单项目文章结构

1. 先给痛点或可见结果
2. 项目一句话
3. 为什么我注意到它：Star、增长、作者、品牌或热点
4. 截图 / Demo 证明
5. 3 个核心亮点
6. 使用方式和门槛
7. 放进我们的 AI 工作流会怎么用
8. 坑和边界
9. 开源地址

## 3. 合集文章结构

开头先说筛选标准。每个项目固定写：

- 它是什么
- 解决什么问题
- 为什么值得收藏
- 使用门槛
- 开源地址

最后给一张“适合谁用”的选择表。

## 4. 截图规则

每个可写仓库至少规划 3 个截图位：

- GitHub 仓库首页
- README/Demo 关键图
- 使用方式或运行结果

如果没实测，明确写“发布前需替换为真实试跑截图”。

## 5. 标题规则

优先：

`实体词 + 具体任务 + 结果/判断`

例子：

- `GitHub 上这个 AI 工具，能把陌生代码库变成一张地图`
- `别急着让 AI 改代码，先让它看懂项目结构`
- `我看了一个 3 万 Star 的项目，发现 AI 读代码正在变成图谱工作流`

少用：

- 神级
- 杀疯了
- 火火火
- YYDS
- 顶啊

## 6. 边界

- 没跑过，不写“实测稳定可用”。
- 没实时增长数据，不写“最近暴涨”。
- 只看 README，就写“从 README 和 Demo 看”。
- 涉及系统配置、Agent 配置、PATH、浏览器、数据库、云资源，提醒风险。
- 涉及爬虫、安全、账号检索、反检测，只讲合法合规用途。
## 7. 2026-06-03 周榜发布补充

GitHub 周榜文章不要先讲“我们怎么筛”。公开正文先讲读者能用的结果。

推荐顺序：

1. 先说明这一组仓库解决哪类问题。
2. 再给一张总览图或短拆截图。
3. 每个仓库只写：是什么、解决什么、适合谁、先怎么试。
4. 最后给选择建议，不写内部写作计划。

截图建议：

- 单仓库短拆解 HTML 比长段文字更适合放进文章。
- 每个仓库卡片用不同版式和配色。
- 截图里不要出现作者栏、公众号名、筛选过程、写作流程。

去重：

- 发布前检查已发布记录。
- 已讲过的仓库，除非重大更新，不重复放进周榜。
